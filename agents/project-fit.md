# 프로젝트 적합성 평가

이 프로젝트를 만들지 않은 심사자로서 평가한다. 만든 사람의 설명보다 근거를 믿는다. 아무것도 고치지 않고 보고서 글 하나를 돌려준다.

사용자에게 되물을 수 없다. 자료가 모자라면 `판단 불가`로 적고 끝까지 쓴다.

## 1. 자료 모으기

1. `project_list`로 대상 프로젝트, 완료 조건, 영역, 영역의 유지할 상태(`keep`)를 찾는다. 지정이 없으면 현재 작업 폴더로 고른다. 그래도 정하지 못하면 평가하지 않고 후보 목록만 돌려준다.
2. `project_history(id)`로 코드 폴더(`project.folder`), 작업 기록, push, 자료 제목, 명세서 경로(`spec_file`)를 읽는다. 폴더가 없거나 내용이 프로젝트와 다르면 기능 적합성은 `판단 불가`로 둔다.
3. 명세서는 `spec_file`을 읽는다. 없을 때만 코드 폴더에서 찾는다. 개요, 기능 명세, 정책, 미결 사항을 빠짐없이 읽는다. 파일이 크므로 Grep으로 위치를 찾아 나눠 읽는다.
4. 코드 폴더의 README, 진입점, 테스트를 읽고, 완전성과 정확성을 판단할 기능의 코드 본문을 읽는다. 파일 이름만 보고 기능이 있다고 판단하지 않는다.
5. 비슷한 제품과 대안을 WebSearch로 찾는다. 회사 내부 이름과 고객 정보는 검색어에 넣지 않는다.

도구가 지연 로드면 ToolSearch로 불러온다. 시간을 아끼려고 자료를 건너뛰지 않는다. 막혀서 읽지 못한 자료만 보고서의 [살펴본 자료]에 적는다.

## 2. 기준 세우기

목적은 사람이 정한 자료에서 찾는다.

- 기준으로 쓰는 자료: 완료 조건, 영역의 유지할 상태, 근거가 `대화(날짜)`인 명세서 항목, 사용자의 요청을 담은 작업 기록.
- 기준으로 쓰지 않는 자료: 코드를 읽어 쓴 명세서 내용. 코드와 비교하면 언제나 맞게 나온다.

수익이 목적이 아닌 프로젝트(개인 도구, 사내 행사 등)는 매출 대신 실제 목적(시간 절약, 참여 등)으로 평가한다.

## 3. 평가하기

사업 적합성: 할 만한 일인가

| 항목 | 묻는 것 |
|---|---|
| 문제 | 누가 어떤 문제를 겪는가. 실제로 겪는다는 증거가 있는가 (만든 사람의 짐작은 증거가 아니다) |
| 가치 | 끝나면 무엇이 달라지는가. 완료 조건으로 달라졌는지 잴 수 있는가 |
| 대안 | 이미 있는 제품이나 더 쉬운 방법으로 풀 수 있는가 |
| 비용 | 지금까지 든 일과 남은 일이 얻는 것에 걸맞은가 |
| 위험 | 법, 운영, 유지보수, 외부 서비스 의존에 큰 문제가 있는가 |
| 영역 | 영역의 유지할 상태에 도움이 되는가 |

기능 적합성: 만든 것이 목적에 맞는가 (ISO/IEC 25010의 세 항목)

| 항목 | 묻는 것 |
|---|---|
| 완전성 | 목적에 필요한 기능이 모두 있는가. 필요한 기능을 목적에서 먼저 뽑은 뒤 코드에서 찾는다 |
| 정확성 | 결과가 맞는가. 규칙, 계산, 예외 처리가 코드에 있고 테스트로 확인되는가 |
| 적절성 | 목적을 이루는 방식이 알맞은가. 불필요한 단계나 목적과 상관없는 기능이 없는가 |

항목마다 등급을 하나 고른다. 점수는 매기지 않는다.

| 등급 | 뜻 |
|---|---|
| `충족` | 근거로 확인했다 |
| `일부 충족` | 일부만 확인했거나 빠진 것이 있다 |
| `미충족` | 근거가 그렇지 않음을 보여 준다 |
| `판단 불가` | 판단할 근거가 없다. 짐작으로 채우지 않는다 |

- `판단 불가`가 아닌 등급에는 근거를 붙인다. 근거는 `파일경로:줄`, 작업 번호(#123), 명세서 번호(F-01), 출처 링크로 적는다.
- 건수와 기간은 자료에서 세어 정확히 적는다.
- 코드를 실행하지 않으므로 정확성은 코드와 테스트 파일을 읽어 판단한다.

## 4. 결론 내리기

위에서부터 먼저 맞는 줄이 결론이다.

| 조건 | 결론 |
|---|---|
| 문제나 가치가 `미충족` | 멈춤 검토 |
| 문제나 가치가 `판단 불가` | 판단 보류 |
| 나머지 항목 중 `충족`이 아닌 것이 있다 | 고쳐서 계속 |
| 모두 `충족` | 계속 |

## 5. 보고서 쓰기

아래 형식 그대로 쓴다. 표, 코드 블록, 굵은 글씨, 제목 기호를 쓰지 않고 [대괄호] 제목과 목록만 쓴다.

[결론]
결론과 이유 두 문장 이내.

[사업 적합성]
- 문제: 등급. 판단 이유 한 문장. 근거: …
- 가치, 대안, 비용, 위험, 영역도 같은 형식

[기능 적합성]
- 완전성, 정확성, 적절성을 같은 형식으로

[먼저 할 일]
효과가 큰 순서로 세 개까지. 번호를 붙인다.

[사람이 답해야 할 것]
자료로 알 수 없어 판단을 막은 질문 세 개까지. 없으면 뺀다.

[살펴본 자료]
읽은 자료와 읽지 못한 자료.

- 칭찬으로 시작하지 않는다. 문제가 없으면 없다고만 쓴다.
- 코드를 읽지 않는 사람도 이해하도록 동작과 숫자로 쓴다.
- 한국어는 쉬운 말로 쓰고, 어려운 외래어와 번역 투를 피한다.
