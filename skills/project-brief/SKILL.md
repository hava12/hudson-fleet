# 사전 기획

명세서보다 먼저, 왜 만드는지와 누구를 위해 만드는지를 대화로 정한다. 결과는 그 프로젝트 기획명세서의 사전 기획 탭이다. 이 탭은 사람이 정한 기준이라 명세서 스킬(project-spec)과 적합성 평가(project-fit)가 기준으로 읽는다.

진행 순서: **0단계 프로젝트 확인 → 1단계 판별 → 2단계 진행 문서 하나 따르기 → 3단계 기록과 보고.**

## 지킬 규칙

- **질문은 한 번에 3개까지 한다.** 고를 수 있는 질문은 `AskUserQuestion`으로, 답이 열린 질문(문제, 증거)은 글로 묻는다.
- **사용자의 말과 확인한 자료만 쓴다.** 빈칸을 짐작으로 채우지 않고 8장 아직 모르는 것(`Q`)에 올린다.
- **검색 결과는 출처 링크와 함께 보여 주고, 사용자가 받아들인 것만 쓴다.** 회사 내부 이름과 고객 정보는 검색어에 넣지 않는다.
- **채택한 내용만 쓴다.** 고르지 않은 안, 뺀 것, 옛 결정은 쓰지 않는다(project-spec의 지킬 규칙과 같다).
- **묻지 못하는 실행이면 시작하지 않는다.** 대시보드 버튼처럼 대화가 없는 실행이면 채팅에서 하자고 알리고 끝낸다.
- **글과 뼈대는 명세서와 같다.** 이 스킬 폴더 옆 `../project-spec/format.md`의 형식을 따르고, 파일을 새로 만들 때는 `../project-spec/template.html`을 뼈대로 쓴다.

## 0단계: 프로젝트 확인

1. `project_list`로 프로젝트를 고른다. 요청, 현재 폴더, 이름, 완료 조건으로 판단하고 후보가 여럿이면 묻는다. 도구가 지연 로드면 ToolSearch로 `select:mcp__plugin_hudson-fleet_fleet__project_list,mcp__plugin_hudson-fleet_fleet__project_history,mcp__plugin_hudson-fleet_fleet__project_save,mcp__plugin_hudson-fleet_fleet__project_folder,mcp__plugin_hudson-fleet_fleet__task_start,mcp__plugin_hudson-fleet_fleet__task_update`
2. 맞는 프로젝트가 없으면 `project_save`로 바로 만든다(상태는 진행 중). 스킬을 실행한 것이 곧 만들겠다는 뜻이므로 따로 묻지 않는다. 명세서 파일 이름과 작업 기록이 프로젝트에 붙으므로 먼저 만든다.
   - 이름: 요청에서 따온 임시 이름으로 만든다. 진짜 이름은 사전 기획 중에 사용자와 협의해 정한다(`new.md` 이름 묶음). 요청에 이름이 있어도 협의를 건너뛰지 않는다.
   - 완료 조건: 임시로 `사전 기획을 마치고 첫 판 범위를 정함`. 사전 기획을 마칠 때 고친다.
   - 코드 폴더: 현재 폴더가 비었거나 README·설정 파일뿐이면 현재 폴더. 다른 프로젝트의 코드가 있는 폴더면 `~/Project/<이름을 영문 소문자와 -로 옮긴 것>`. 없는 폴더는 바로 위 폴더가 있을 때 도구가 만든다.
   - 이름이 비슷한 프로젝트가 있으면 만들지 말고 그 프로젝트인지 묻는다. 같은 일을 두 번 만들지 않기 위해서다.
   - 만든 프로젝트의 번호, 이름, 코드 폴더는 1단계 판별을 확인받을 때 함께 알린다. 바꾸자고 하면 `project_save(id, name)`, `project_folder(id, folder)`로 고친다.
3. `project_history(id)`로 명세서 경로(`spec_file`), 코드 폴더(`project.folder`), 작업 기록을 읽는다.
4. `task_start`로 이 일을 기록한다(tag `기획`, project에 그 id).

## 1단계: 판별

명세서와 코드를 보고 상황을 판별한다.

- 사전 기획 탭이 있는가: 명세서에 `id="brief-problem"`이 있다
- 기획 편 기능 명세가 있는가: `id="features"` 장에 `F-` 번호가 있다
- 코드가 있는가: 코드 폴더에 README와 설정 파일 말고 다른 파일이 있다

| 요청 | 상황 | 판별 | 따를 문서 |
|---|---|---|---|
| 사전 기획, 새 서비스 | 사전 기획 탭이 없고 코드도 없음 | 새 프로젝트 | `new.md` |
| 사전 기획 | 사전 기획 탭이 없고 코드는 있음 | 만든 제품의 사전 기획 | `new.md` (답 일부를 코드와 기록에서 채움) |
| 사전 기획, 방향 바꾸기 | 사전 기획 탭이 있음 | 방향 전환 | `new.md` (있는 내용을 고쳐 씀) |
| 기능 추가 | 기획 편 기능 명세가 있음 | 기능 추가 | `feature.md` |
| 기능 추가 | 기획 편이 없고 코드는 있음 | 명세서 먼저 | 기능 번호를 붙일 곳이 없으므로 project-spec으로 명세서를 먼저 만들자고 권함 |
| 기능 추가 | 명세서도 코드도 없음 | 새 프로젝트 | `new.md` |

- 요청이 애매하면("이거 기획하자") 상황으로 고른다. 사전 기획 탭이 없으면 새 프로젝트, 있으면 방향 전환인지 기능 추가인지 묻는다.
- 대상이나 핵심 가치가 바뀐다는 말이 나오면 기능 추가 중이라도 방향 전환으로 바꾸자고 한다.
- **판별 결과는 근거와 함께 한 번 확인받는다.** 판별이 틀리면 질문이 통째로 틀어진다.
  - 예: "명세서에 사전 기획 탭이 있고 기능이 25개 있어 기능 추가로 진행합니다."

## 2단계: 진행

판별에 맞는 문서 하나만 이 스킬 폴더에서 읽고 그대로 따른다.

- `new.md`: 새 프로젝트, 만든 제품의 사전 기획, 방향 전환
- `feature.md`: 기능 추가

## 3단계: 기록과 보고

- `task_update(id, "done")`로 끝낸다. note에는 쓴 장이나 더한 기능 번호를 적는다.
- 대화 중에 미룬 일과 판단할 날은 `task_start`로 남은 일을 남긴다. 예: `F-26 판단: 2026-11-22에 재방문율 7% 기준으로 봄`
- 보고에 담을 것:
  - 파일 전체 경로와 여는 명령(`! open <경로>`)
  - 쓰거나 고친 장, 더한 기능 번호
  - 열린 `Q` 목록
  - 다음 단계: 진행 문서의 마무리에 적힌 것
