# 기능 추가 검토

결과는 기획 5장의 예정 기능 하나다. 필요하면 6장 정책과 10장 미결 사항도 더한다.

## 1. 읽기

명세서에서 읽는다: 사전 기획 탭(있으면 문제, 성공 기준, 핵심 기능), 기획 1장 범위와 성공 기준, 4장 화면 목록, 5장 기능, 6장 정책.

사전 기획 탭이 없으면 성공 기준 대신 fleet 완료 조건과 비교한다. 보고할 때 사전 기획을 해 두면 다음 검토가 쉬워진다고 한 줄 권한다.

## 2. 짧은 검토

아래 3가지를 한 번에 묻는다. 요청에 이미 답이 있으면 뺀다.

1. 어떤 문제를 푸나요? 누가 요청했거나 어디서 봤나요?
2. 성공 기준의 어느 숫자에 도움이 되나요?
3. 더 쉬운 방법은 없을까요? 묻기 전에 후보를 먼저 제안한다: 있는 기능 고치기, 설정값 바꾸기, 손으로 하기.

## 3. 겹침과 부딪침 확인

- 비슷한 기능이 5장에 이미 있으면 새 기능 대신 그 기능을 고치자고 제안한다.
- 정책(`P-`)과 부딪치면 어느 쪽을 따를지 묻는다.
- 바뀌는 화면(`S-`)이 있으면 번호를 적어 둔다.
- 성공 기준과 상관없는 기능이면 그렇다고 말한다. 넣을지는 사용자가 정한다.

## 4. 결정

- 넣기로 하면 5단계로 간다.
- 넣지 않기로 하면 명세서에 쓰지 않는다. 이 일의 fleet 작업을 `rejected`로 끝내고 note에 이유를 적는다.
- 나중에 하기로 하면 명세서에 쓰지 않고 fleet 남은 일로 남긴다.

## 5. 명세서에 쓰기

형식은 `../project-spec/format.md`를 따른다.

- **기획 5장**: 맞는 묶음 아래에 항목 하나를 더한다.
  - 번호는 문서 전체에서 가장 큰 `F` 번호의 다음 번호다.
  - 상태는 `예정`, 근거는 `대화(날짜)`, 이름 옆 `.ref`에 바뀌는 화면 번호를 적는다.
  - 항목 끝 ※ 줄에 판단 기준을 적는다: `판단할 날: YYYY-MM-DD, 기준: …`
- **기획 6장**: 새 규칙이 생기면 다음 `P` 번호로 더한다.
- **기획 10장**: 아직 모르는 것은 다음 `Q` 번호로 올린다.
- **기획 1장**: 현재 상태의 기능 개수를 고친다.
- **개발 3장**: 개발 편이 있으면 진행 히스토리에 한 줄을 더한다.
- 머리말의 문서 버전을 올리고 기획 편 기준일을 오늘로 바꾼다.

## 6. 마무리

- 판단할 날을 fleet 남은 일로 남긴다.
- 다음 단계를 알린다.
  - 화면이 바뀌면 기획 4장 화면 정의를 먼저 고친다.
  - 불확실한 기능이면 project-mvp로 작은 데모를 만들어 시험한다.
  - 개발 작업을 기록할 때 이 기능 번호를 함께 적는다.
