# 새 프로젝트 사전 기획

결과는 기획명세서 사전 기획 탭의 8개 장이다. 만든 제품의 사전 기획과 방향 전환도 이 문서를 따른다.

## 1. 파일 준비

- `spec_file`이 없으면 `../project-spec/template.html`로 만든다.
  - 사전 기획 탭만 채운다. 기획 편과 개발 편 탭은 뼈대 주석의 "아직 만들지 않았어요" 한 줄만 남긴다.
  - 문서 제목은 프로젝트 이름, 한 줄 정의는 3장에서 정한 것을 쓴다.
- `spec_file`이 있으면 먼저 읽는다.
  - 사전 기획 탭이 없으면 뼈대에서 탭 단추와 탭을 옮겨 넣는다. 다른 탭의 내용은 건드리지 않는다.
  - `<style>`과 `<script type="module">`은 뼈대 것으로 바꾼다. 옛 스크립트는 탭 세 개를 다루지 못한다.
- 질문 묶음이 끝날 때마다 그 장을 파일에 쓴다. 대화가 길어 끊겨도 정한 것이 남는다.

## 2. 질문 묶음

한 묶음에 질문 3개까지 묻는다. 묶음이 끝나면 정리해 확인받고 그 장을 쓴다.

| 묶음 | 묻는 것 | 쓰는 장 |
|---|---|---|
| 1. 문제 | 누가 어떤 불편을 겪나요? 실제로 겪는 것을 본 적이 있나요(본인 경험, 들은 말, 숫자)? 지금은 그 불편을 어떻게 넘기고 있나요? | 1장, 4장 지금 하는 방법 |
| 2. 대상과 가치 | 누가, 몇 명이 쓰나요? 언제 어떤 상황에서 쓰나요? 다 만들면 그 사람에게 무엇이 달라지나요? | 2장, 3장 |
| 리서치 | 묻지 않고 검색한다. 비슷한 제품 3~5개와 더 쉬운 대안을 표로 보여 주고, 그것으로 충분하지 않은 이유를 묻는다 | 4장 |
| 3. 성공과 핵심 기능 | 어떤 숫자가 되면 성공인가요? 언제 판단할까요? 꼭 있어야 하는 기능 3~5개는 무엇인가요? | 5장, 6장 |
| 4. 제약과 위험 | 기한과 비용은 어떤가요? 법이나 개인정보 문제가 있나요? 꼭 써야 하는 외부 서비스가 있나요? | 7장 |
| 5. 이름 | 원하는 느낌과 모양(영어·한국어, 한 단어·두 단어)을 묻고 후보 3~5개를 낸다. 후보마다 같은 이름의 제품과 주소(.com·.kr 등)가 있는지 검색해 함께 보여 준다 | 문서 제목, 3장 `(제목)` |

- 요청, 완료 조건, 앞선 답에 이미 나온 질문은 건너뛴다. **5. 이름은 예외다.** 요청에 이름이 있어도 사용자와 확정할 때까지 협의한다.
- 이름을 정하면 바로 옮긴다: `project_save(id, name)` → `project_history(id)`의 새 `spec_file` 경로로 명세서 파일을 옮김 → 코드 폴더가 비어 있으면 새 이름 폴더로 `project_folder(id, folder)` 하고 빈 옛 폴더를 지움. 명세서 파일 이름은 프로젝트 이름을 따르지만 저절로 옮겨지지 않는다.
- **만든 제품의 사전 기획**이면 README, 작업 기록, 명세서에서 찾은 답을 먼저 채워 보여 주고 맞는지만 묻는다. 증거와 성공 기준은 코드에 없으므로 꼭 묻는다.
- **방향 전환**이면 지금 내용을 보여 주고 바뀌는 장만 다시 묻는다. 바뀐 결과만 쓰고 옛 내용은 지운다. 개발 편 진행 히스토리가 있으면 한 줄 남긴다.

## 3. 짐작 막기

- 만든 사람의 짐작은 증거가 아니다. 증거가 없으면 1장 증거에 `아직 없음`이라 쓰고 `Q`로 올린 뒤, 확인할 방법을 제안한다(예: 대상 다섯 명에게 묻기).
- 성공 기준에는 잴 수 있는 숫자와 판단할 날이 있어야 한다. 답이 없으면 예시 숫자 두세 개를 제안해 고르게 한다.
- 핵심 기능이 5개를 넘으면 줄이자고 한다. 많을수록 첫 판이 늦어지고 무엇이 먹혔는지 알기 어렵다.
- 검색에서 이미 충분히 푸는 제품이 나오면 숨기지 말고 먼저 말한다. 만들지 말자는 결론도 좋은 결과다.

## 4. 장별 쓰는 법

뼈대의 장 순서와 `id`를 그대로 쓴다. 형식은 `../project-spec/format.md`를 따른다.

| 장 | 쓰는 법 |
|---|---|
| 1. 문제 | 주제 두 개: 누가 어떤 불편을 겪는가, 겪는다는 증거. 끝에 ※ 줄로 `근거: 대화(날짜)` |
| 2. 대상 | 소제목 `(누가)`, `(얼마나)`, `(어떤 상황에서)` |
| 3. 가치 | 소제목 `(한 줄 정의)`, `(달라지는 것)`. 한 줄 정의는 문서 머리에도 쓴다 |
| 4. 대안 | `(지금 하는 방법)` 한 줄과 `대안 \| 하는 일 \| 모자란 점 \| 출처` 표. 출처는 링크 |
| 5. 성공 기준 | 항목마다 세부로 `잴 방법`과 `판단할 날` |
| 6. 핵심 기능 | 기능 이름과 한 줄 설명. 기능 번호(`F-`)는 기획 편에서 붙이므로 여기서는 붙이지 않는다 |
| 7. 제약과 위험 | 소제목 `(기한)`, `(비용)`, `(법·운영)`, `(외부 서비스)`. 없으면 `해당 없음` |
| 8. 아직 모르는 것 | `번호 \| 확인할 것 \| 나온 곳 \| 물어볼 사람 \| 상태` 표. 번호는 문서 전체에서 가장 큰 `Q` 번호의 다음 번호 |

- 머리말의 문서 버전을 올리고 사전 기획 기준일을 오늘로 바꾼다.
- 다 쓴 뒤 `format.md` 점검표에서 해당하는 것을 확인한다.

## 5. 마무리

- **판단 1(만들 만한가)**: 적합성 평가 에이전트(`hudson-fleet:project-fit`)를 돌려 볼지 권한다. 문제나 가치가 약하면 여기서 멈춰도 된다고 알린다.
- **완료 조건**: 5장 성공 기준을 120자 이내 한 줄로 다듬어 `project_save(id, done_when)`로 바로 고치고, 바꾼 문장을 보고에 적는다. 사용자가 다르게 하자고 하면 다시 고친다.
- **판단할 날**: 5장의 판단할 날을 fleet 남은 일로 남긴다.
- **다음 단계**: "기획명세서 만들어 줘"라고 하면 project-spec이 이 탭을 기준으로 기획 편을 쓴다.
