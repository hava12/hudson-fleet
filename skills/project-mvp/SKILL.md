# 첫 판과 데모 만들기

명세서를 기준으로 처음 출시할 범위를 정하고, 그 범위에서 가장 불확실한 부분을 작은 데모로 시험한다.

- **첫 판(MVP)**: 처음 출시할 범위. 제품 결정이다.
- **데모**: 첫 판의 불확실한 부분에 답을 얻는 작은 결과물. 첫 판의 축소판이 아니다.

두 가지를 나누는 이유가 있다. 첫 판 전체를 데모로 만들면 오래 걸리고 무엇을 시험하는지 흐려진다. 질문 하나에 답하는 데모는 하루 안에 끝나고 다음 결정을 바로 바꾼다.

진행 순서: **0단계 명세서 찾기 → 1단계 첫 판 정하기 → 2단계 데모 범위 정하기 → 3단계 만들기 → 4단계 검증 → 5단계 명세서 반영 → 6단계 보고.**

1단계와 2단계에서 사용자 확인을 받기 전에는 데모를 만들지 않는다. 범위가 틀리면 만든 것을 모두 버려야 하기 때문이다.

## 지킬 규칙

- **명세서가 기준이다.** 첫 판 범위는 명세서에만 적는다. 데모 폴더나 별도 파일에 따로 두면 실행할 때마다 범위가 달라진다.
- **첫 판은 사용자가 정한다.** 이 스킬은 초안을 제안할 뿐이다.
- **규칙을 조용히 바꾸지 않는다.** 만들다가 명세서와 다른 규칙이 필요해지면 그대로 쓰지 말고 무엇이 왜 다른지 알린다. 사용자가 받아들이면 5단계에서 명세서를 고친다.
- **쉬운 쪽으로 바꾸지 않는다.** 시험할 규칙을 만들기 쉬운 규칙으로 바꾸면 데모의 답이 쓸모없어진다. 임시 처리는 시험 대상이 아닌 부분에만 쓴다.
- **본 것만 말한다.** 자동 검증으로 확인한 것과 사람이 봐야 아는 것을 나눠 보고한다.
- **비밀 값은 쓰지 않는다.** 키, 토큰, 개인정보를 코드와 문서에 넣지 않는다.

## 0단계: 명세서 찾기

1. hudson-fleet 프로젝트면 `project_list`로 프로젝트를 고르고 `project_history(id)`의 `spec_file`을 쓴다. 도구가 지연 로드면 ToolSearch로 `select:mcp__plugin_hudson-fleet_fleet__project_list,mcp__plugin_hudson-fleet_fleet__project_history`
2. 없으면 현재 폴더의 `<폴더이름>-기획명세서.html`을 쓴다.
3. 명세서가 없으면 멈추고 `project-spec` 스킬을 먼저 돌리자고 말한다. 기준 없이 범위를 정하면 근거를 대지 못한다.

명세서에서 읽을 것: 기획 1장(목적, 범위, 성공 기준), 5장(기능과 상태), 6장(정책), 10장과 개발 4장(열린 미결 사항), 개발 3장(다음 할 일).

프로젝트 폴더의 코드도 읽는다. 이미 데모가 있으면 새로 만들지 말고 고칠 곳을 찾는다.

## 1단계: 첫 판 정하기

기획 1장 범위에 `(첫 판)`으로 표시한 항목이 있으면 그 범위를 쓰고 2단계로 간다. 사용자가 바꾸자고 할 때만 다시 정한다.

없으면 초안을 만든다. 기능마다 세 가지로 나눈다.

| 분류 | 뜻 | 판단 기준 |
|---|---|---|
| 포함 | 첫 판에 넣는다 | 이게 없으면 성공 기준을 확인할 수 없다 |
| 임시 처리 | 간단하게 대신한다 | 필요하지만 손으로 하거나 고정값으로 대신해도 사용자가 눈치채지 못한다 |
| 뺌 | 첫 판 뒤로 미룬다 | 없어도 사용자가 처음 한 번 쓰는 길이 끊기지 않는다 |

사용자가 처음 들어와 핵심 가치를 맛보고 끝낼 때까지의 길을 먼저 그린다. 그 길에 없는 기능은 뺌이 기본이다. 포함이 많아지면 초안을 다시 줄인다. 첫 판이 크면 출시가 늦어지고 무엇이 먹혔는지도 알기 어렵다.

초안은 이 표로 보여 주고 확인을 받는다. `AskUserQuestion`이 있으면 그것으로 묻는다.

| 기능 | 분류 | 이유 |
|---|---|---|
| F-26 쟁탈전 | 포함 | 핵심 가치를 직접 만듦 |

확정하면 기획 1장 범위에 적는다. 번호(`F-xx`)만 쓰고 내용을 되풀이하지 않는다. 글의 형식은 같은 플러그인의 `skills/project-spec/format.md`를 따른다.

```html
<li><b>(첫 판)</b> F-26, F-29, F-38</li>
<li><b>(첫 판 임시 처리)</b> F-34: 연합을 미리 만들어 둠</li>
<li><b>(첫 판에서 뺌)</b> F-10, F-17</li>
```

## 2단계: 데모 범위 정하기

첫 판에서 가장 불확실한 것을 찾는다. 찾을 곳은 명세서의 임시안, `확인 필요`, 제안값, 그리고 한 번도 시험하지 않은 핵심 규칙이다.

불확실한 것을 **확인할 질문 1~2개**로 줄인다. 질문마다 어떤 결과면 통과인지 함께 적는다.

```
질문: 칸을 모아 구를 통합하는 과정이 재미있는가
통과 판단: 시험한 사람이 다음 구를 스스로 노리는가
```

질문에 답하는 데 필요한 것만 데모에 넣는다. 로그인, 서버, 저장, 관리 화면은 질문이 그것을 묻지 않는 한 넣지 않는다.

질문과 데모 범위를 보여 주고 확인을 받는다. 기존 데모를 고칠 때는 무엇을 바꾸고 무엇을 그대로 두는지도 적는다.

## 3단계: 만들기

프로젝트에 정해진 기술이 있으면 따른다. 없으면 서버 없이 브라우저에서 바로 열리는 파일을 기본으로 한다. 시험하는 사람이 설치 없이 열 수 있어야 소감을 빨리 받는다.

- **규칙과 화면을 나눈다.** 규칙 파일은 화면을 모르고, 같은 입력이면 같은 결과를 낸다. 그래야 점검과 모의 실험을 돌릴 수 있고 나중에 서버로 옮길 수 있다.
- **값에 번호를 단다.** 규칙의 값마다 `P-xx`나 `Q-xx`를 주석으로 적는다. 명세서에 없는 값은 제안값이라고 적는다. 시험 뒤 어디를 고칠지 바로 찾기 위해서다.
- **값은 모의 실험으로 고른다.** 재미나 균형을 좌우하는 값은 감으로 정하지 말고, 규칙 파일로 여러 조합이나 플레이 방식을 돌려 비교한다. 단순한 방식이 고득점을 내거나 선공이 항상 이기는 문제는 이렇게 먼저 드러난다. 쓴 실험 코드는 지우지 말고 결과를 5단계에서 미결 사항에 적는다.
- **점검 코드를 남긴다.** 규칙 파일 옆에 실행 파일 하나를 두고 명세서 번호 기준으로 규칙을 확인한다. 테스트 도구를 새로 들이지 않는다.
- **그림과 소리를 코드로 흉내 내지 않는다.** 사용자가 준 파일을 연결하고, 없으면 글자나 단순한 도형으로 임시 표시를 한다. 코드로 그린 캐릭터는 시험 결과를 흐린다. 사용자가 원하면 예외로 둔다.
- **핵심 장면으로 바로 가는 길을 둔다.** 주소 끝의 표시 같은 방법으로 시험할 장면을 바로 열게 한다. 재생 검증도 이 길을 쓴다.
- **뺀 것을 표시한다.** 데모라서 대신한 부분은 주석에 적는다.

## 4단계: 검증

1. 점검 코드를 실행한다.
2. 브라우저 자동 재생으로 처음부터 끝까지 한 번 돌린다. 스크립트 오류가 없어야 한다. 화면이 있으면 휴대폰 폭(360px)도 확인한다.
3. 시험할 장면의 사진을 찍어 직접 본다.

자동으로 알 수 없는 것은 판단하지 않는다. 재미, 움직임의 느낌, 실제 휴대폰에서의 조작감은 `사람 확인 필요`로 남긴다. 멈춘 사진만 보고 움직임이 좋다고 말하면 안 된다. 실패하면 고치고 다시 돌리며, 끝내 못 고치면 그대로 보고한다.

## 5단계: 명세서 반영

`spec_file`이나 찾은 명세서를 고친다. 번호는 바꾸지 않고 새것만 다음 번호를 붙인다. 형식은 `skills/project-spec/format.md`를 따른다.

- 기획 5장: 데모에서 도는 기능의 상태를 `개발 중`으로 고치고 근거 `파일:줄`을 적는다. 데모의 제약은 ※ 줄에 쓴다.
- 기획 6장: 사용자가 받아들인 규칙과 값을 고친다.
- 기획 10장·개발 4장: 모의 실험 결과를 해당 미결 사항에 적는다. 풀린 것은 `해결`로 바꾼다.
- 개발 3장: 진행 히스토리에 한 줄을 더하고 다음 할 일을 고친다.
- 머리말: 문서 버전을 올리고 고친 편의 기준일을 오늘로 바꾼다.

고친 뒤 번호가 어긋나지 않았는지 확인한다.

## 6단계: 보고

- 여는 방법(파일 경로나 명령)
- 확인할 질문과 통과 판단
- 사용자가 직접 해 볼 일 1~2개
- 검증 결과: 통과한 것, 사람 확인이 필요한 것, 실패한 것
- 모의 실험으로 바꾼 값

소감을 받으면 제안값을 고치고 3단계부터 다시 돈다. 답이 나온 질문은 명세서에 적는다.
